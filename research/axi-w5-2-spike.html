Q1 — SubagentStop identity plumbing

SOLVEDMechanism: spawn-name mandate + payload.agent_type

W5-1's wake classifier keys benign/actionable stubs by agent identity, but the native SubagentStop payload was assumed identity-blind — the production reader (timing-capture.js) only ever extracted session_id and tool_use_id on stop. This spike checked that assumption against a live runtime instead of trusting the assumption.

Ground-truth capture method

Temporarily instrumented the plugin-cache timing-capture.js hook (on both SubagentStop and PreToolUse) to dump raw, unfiltered payloads to disk. Captured 7 stop samples plus matching spawn samples across 3 live sessions. The instrument was restored to its original state and verified clean afterward — no residue left in the production hook.

Key facts from the capture

  • agent_type = the Agent tool's name: param VERBATIM when passed; empty string when not passed (3 of the 7 samples were name-less, from other sessions not following the naming convention).
  • agent_id embeds the spawn name for named spawns but the format is fragile — deliberately not parsed.
  • last_assistant_message carries the subagent's full final text intact — one captured sample (an R2 report) arrived at 7,304 characters with no truncation. This is what makes live-record classification possible before Apex ever reads the agent's output file.
  • No tool_use_id on stop, confirmed two ways: 2,200/2,200 fleet events agree, and the documented schema agrees. This is by design, not a regression.
  • Spawn-side events (PreToolUse/PostToolUse) do carry tool_use_id, tool_input.name, subagent_type, and model — richer, but unnecessary once agent_type is available on stop.
  • Anomaly flagged for post-adoption watch: one spawn produced two stop events with different agent_type values (name vs. subagent_type) and different last_assistant_message lengths. The classifier's fail-open behavior handles this correctly today — an unresolved key falls through to actionable — but it's worth monitoring once the mechanism is live.

Mechanism, end to end

  1. Spawn-name mandate. execute.md now requires every Agent spawn to pass name: "<agent-name>" — the same string as its wake-bookkeeping stub filename.
  2. Stub resolution. On SubagentStop, the classifier tries payload.agent_type first (falling back through agent, subagent_type, tool_use_id, etc. for unnamed or legacy spawns) to find the on-disk agent-record stub.
  3. Live-record merge. The stub usually still says "spawned" at stop time, because Apex hasn't read the agent's output yet. last_assistant_message is scanned backwards from the tail for a balanced-brace JSON object carrying a status field — the agent's own typed completion record — so the last status-bearing object wins (records come last by convention, so a decoy object earlier in the message can't win). The stub still wins for wave bookkeeping (isLastInWave), which the message can't know.
  4. Escalate-only merge, trust decision. The merge is asymmetric: if the stub alone already classifies actionable, it wins outright and a stale or hallucinated "passed" in the message can never de-escalate it back to benign. The message can only escalate a non-actionable stub — a hallucinated or injected "passed" can absorb the stub only because the stub still says "spawned" (non-actionable) at that point; a genuinely failed agent surfaces through the same path via its own message reporting status: "failed", which escalates regardless of what the stub says.

Q2 — Synchronous waves

DO NOT ADOPTKeep never-block + classifier instead

The Wave 5 spec proposed dispatching a wave with run_in_background: false so Apex blocks once per wave instead of waking once per completion — the only path to true zero-token idle. This spike measured whether that trade is worth taking, and whether the primitive even exists.

Findings

TypeFinding
BLOCKERA probe spawned with run_in_background: false did not block the parent turn on the installed runtime (v2.1.198) — the harness spawns asynchronously regardless, and the orchestrator kept executing further tool calls while the probe was still running. Synchronous waves as specced are not implementable on this runtime today.
MEASUREDSession 599d3b95 (AXI-PORT W1+W5, $63.11 total): 496 assistant turns, 57 agent spawns → 84 SubagentStop events → 66 wake turns. Those wake turns alone consumed 20.95M cache-read tokens (≈ $31 at Opus $1.50/M cache-read) — roughly half the session's total cost. Median re-read per wake: 301k tokens.
MEASUREDOnly 9 of 66 wakes were pure acks (no tool call, under 300 output tokens) — those 9 account for 2.74M cache-read (≈ $4.11). The other 57 wakes did real work: reading agent output, re-tasking, dispatching the next wave.
MODELEDA working classifier (Q1's identity mechanism) absorbs benign mid-wave stops, consolidating N wake-turns per wave into one wave-end turn. At 2/3 absorption, that's ≈16.8M cache-read saved ≈ $25/session — approximately the same consolidation synchronous waves would have bought, without losing the ability to re-task mid-wave.
QUALITATIVEThis repo's #1 observed failure mode (per learnings/workflow.md) is agents going idle without reporting. Recovering from that requires a live Apex able to SendMessage and re-task mid-wave — a blocked Apex can't do that. Synchronous waves would also freeze user interactivity for the whole wave duration.

Recommendation

Keep apex.md's never-block law as-is. Ship Q1's identity plumbing to activate benign-stop absorption — it captures roughly the same token savings synchronous waves promised, at a fraction of the risk. Revisit synchronous waves only if the runtime ever ships true blocking parallel spawns and the idle-agent recovery problem is solved some other way.

What shipped

Prototype landed at plugin version 0.1.38 (up from 0.1.37):

  • commands/execute.md — added the spawn-name mandate: every Agent spawn must pass name: matching its stub filename, since that's how the classifier resolves payload.agent_type back to the stub.
  • hooks/wake-classifier.js — readAgentRecordFile now tries payload.agent_type as the first resolution key. Split the old resolveRecord into resolveStubRecord (on-disk/env stub) and a new extractMessageRecord (scans last_assistant_message for a balanced-brace JSON object carrying a status field, never throwing on malformed input). A new mergeRecords layers the live message record over the stub, escalate-only, with wave bookkeeping always sourced from the stub.
  • test/wake-classifier.test.js — 13 new tests: agent_type resolving the stub, an empty agent_type falling through to actionable, a failed message record overriding a spawned stub, a passed message record producing benign absorption, a garbage/non-JSON message falling back to stub behavior, a message-only record with no wave surfacing as actionable, an explicit prompt-injection resistance case confirming an injected "passed" only absorbs because the stub already permits it, a decoy-before-failure case, a failed-stub-vs-passed-message escalate-only case, a 100KB pathological input case completing under 2s, and three cases pinning the truncated-scan fix below.

Review hardening. Two Gaze passes on the message-extraction path caught 4 P1s total, all fixed before merge. First pass (3 findings): a first-match decoy could let an earlier non-record brace object win over the real trailing record (fixed by scanning backwards from the tail); the merge could let a stale or hallucinated "passed" message de-escalate an already-actionable stub (fixed by making the merge escalate-only); and the extraction scan was unbounded, so brace-dense untrusted input could spin the synchronous hook (fixed with a 32KB tail window and a 50-candidate attempt cap). Second pass (1 finding, in the first pass's own fix): the 32KB/50-brace truncation fallback was stub-governed — a failure record pushed outside the scan window would silently absorb into a benign "spawned" mid-wave stub. Fixed by having a capped scan that finds no record escalate to actionable('record-truncated') instead of absorbing; the capped-with-record and uncapped-prose paths are unchanged. Test count moved from 254 to 257 to 260.
